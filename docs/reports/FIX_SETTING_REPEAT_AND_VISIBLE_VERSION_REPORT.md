# Повторный отказ числового аргумента и видимая версия

Дата: 24.10.2026. Основа: `2aea9b5da4fd11a750074d76766935abc57ba175`. Реализация завершена локально, ожидает независимого ревью ведущего. Git-мутаций, установки плагина и настоящего STE/LLM-прогона нет.

## Что воспроизведено

До изменения runtime добавлен тест действительного пути `AgentService → ChatCompletionsClient → JSON provider response → llm_arguments → strict validate → SlicerAdapter/QtBridge → fake STE`. Подменена только сеть провайдера и приложение; реальный сетевой запрос не выполнялся.

Для `layer_height` и `cylindrical_layer_height` проверены число `0.12` и точная строка `"0.12"`: ровно один вызов adapter.set_setting с float и исходным запрошенным ключом; before=0.1, after=0.12, отдельный get_setting=0.12. Только строка получает прежние argument_admission и детерминированное уведомление в assistant_message. Число не получает ложного уведомления. Смена другого ключа/режима не выполняется.

Для обоих ключей строка с лишним полем либо global `extruder_id:null` отвергается до API: `invalid_tool_arguments`, `stage=validation`, `executed=false`, ноль записей. Поля не отбрасываются. Также проверены пробелы, двойная строковая обёртка, запятая, единицы, overflow, underflow, слишком длинная строка, приватные маркеры и отсутствие утечки неизвестного имени/ключа.

**Обход нормализатора не воспроизведён.** Повторный отказ пользователя не объявляется исправленным. Ни полные payload, ни версия обслуживавшей его установленной копии не известны. Старая копия и иной payload остаются гипотезами; объяснение модели о транспортном преобразовании не доказано. Лексика/объём допуска не расширялись.

## Изменения

- `plugin/AIAssistant/agent/tools.py`: необязательная компактная диагностика решения LLM-нормализатора. Фиксированные reason, policy, normalizer_present, типы и количества/наличие полей; без raw значений, произвольных имён, путей и секретов. Общий type helper сохраняет прежний формат validation summary.
- `agent/service.py`: передача диагностики в результат tool_finished/контекст провайдера; сведения выпуска в существующем `/api/status`. При некорректном JSON диагностируется invalid_argument_object. Прежний реестр, QtBridge, runtime metadata/guards и бюджеты не менялись.
- `plugin.json` и новый `release.py`: общий источник версии **0.1.1**, release_id **numeric-diag-r1**, numeric_argument_policy **strict-json-numeric-v1**; API остаётся5. Модуль читает собственный manifest при загрузке, наружу возвращает только три публичных поля. В справочных исходниках UM PluginRegistry проверено сохранение дополнительных полей plugin.json; внешние исходники не менялись.
- `web/index.html`, `style.css`, `app.js`: версия внизу левой панели; прежние элементы находятся в прокручиваемом контейнере над ней. Номер версии не дублируется в JS: SPA имеет только маркеры совместимости release/policy, их совпадение с manifest проверяется тестом. Нет Git/process_id/времени в номере выпуска.
- `tests/test_setting_repeat_release.py`: четыре адресных теста с несколькими подслучаями, включая реальный client/service, отсутствие native-вызова при отказе, безопасную диагностику и единственный источник metadata. `tests/test_agent_web.js`: сохранены32 сценария, добавлены4 сценария версии/старого backend/несовпадения выпуска/политики.
- `README.md`, `plugin/README.md`, `docs/API_CONTRACT.md`: фактические поля, границы доказательств, обновление целой копии и отдельное восстановление исходной высоты.

Пример безопасного решения: `reason=invalid_structure`, `value_type=string`, `unexpected_fields_count=1`, `extruder_id_present=true`, `extruder_id_type=null`. Наличие нормализатора отдельно обозначено normalizer_present/policy. Это не отменяет последующую strict validation и не свидетельствует о записи в STE. Прямой MCP строковые значения числового параметра по-прежнему не принимает. Bool/enum, scope/ID, единицы/выражения не исправляются. Правила повтора после validation/preflight/execution/unknown сохранены.

## Проверка установленной копии пользователем

Самому исполнителю установка не разрешена и не выполнялась. Пользователь сохраняет проект, закрывает STE, делает резервную копию старого каталога, заменяет **весь AIAssistant**, перезапускает STE и открывает новый адрес через меню. Ожидается `AI Assistant 0.1.1 · numeric-diag-r1`, вторая строка `Числовой разбор: strict-json-numeric-v1`.

Без поля backend показано точно: «Версия сервера не определена — обновите плагин и перезапустите STE Slicer». При несовпадении release/policy — явное предупреждение. Метка не обещает успешный native write; старая полностью неизменённая SPA может вообще не иметь новой надписи.

Точный промпт: «Прочитай исходное global layer_height. Измени только layer_height на 0.12 мм, если метаданные разрешают. Перечитай get_setting и покажи реальное значение. При ошибке остановись, другой ключ или режим не меняй». Сверить before/after/readback и UI. Затем отдельный запрос: «Восстанови только global layer_height в исходное значение X мм и перечитай get_setting», подставив сохранённое число. При unknown сначала чтение/UI. Если снова отказ — нужны видимая метка и безопасные argument_diagnostics/arguments_summary, без ключа провайдера и приватных payload. Эти инструкции не исполнялись.

## Ограничения и передача

Настоящий провайдер, установленный плагин, STE/native запись, пользовательская ошибка и ручная приёмка не проверены. Нормализация входа не равна успешному изменению настройки. Никаких AppData/Preferences/ключей/принтера, стороннего большого UI/files-ТЗ или следующих этапов не затронуто. Прежняя frozen-копия и helper не менялись. Чужие начальные изменения `docs/COORDINATION.md` и файл текущего ТЗ сохранены.

Исполнитель не выполнял git add/commit/push/merge и останавливается после отчёта. Ведущий проводит независимое ревью; по последнему уточнению разрешённая ему публикация принятого результата — в **новую `codex/fix-setting-version`**, не main. Исполнитель ветку не создаёт и сообщения в другой чат повторно не отправляет: предыдущее уведомление было отклонено автоматической проверкой из-за неподтверждённой авторизации; ведущий получает результат через ожидание этого чата.
