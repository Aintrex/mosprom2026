# Проверка ведущего: ТЗ 01

Дата: 23.10.2026. Проверены отчёт исполнителя, изменения кода, новый Qt-мост, тесты и использованные точки API в справочных исходниках.

## Решение

**Дополнение по результатам совместного прогона: ТЗ 01 принято.** Runtime-приёмка на STE Slicer 7.10.12, Hybrid 530 V5.2.4, 3D зафиксирована в [TASK_01_RUNTIME.md](TASK_01_RUNTIME.md). Ниже сохранены результаты первоначального ревью и список ручных проверок, которые на тот момент ещё ожидались.

## Что проверено независимо

- Перезапущено `python -m unittest discover -s tests -v` на bundled Python 3.13.6: **21 тест, OK**. В песочнице две HTTP-проверки сначала упёрлись в WinError 10013; повтор с разрешённым loopback прошёл полностью. Проверки не отключались.
- `git diff --check`: без замечаний.
- Вызовы стека из worker действительно передаются в callback; основной поток не ждёт Event. Подмена scheduler разделяет постановку и исполнение.
- При timeout до старта отложенная запись отменяется; при начатом вызове сообщается неопределённость. Shutdown отменяет ожидающие вызовы.
- Проверяются фактическое after, типы/конечность чисел, жёсткие границы и отсутствие активной машины. Внутренняя ошибка API не маскируется как Unknown tool.
- Dev-режим без Qt не имитирует успешное чтение/запись; MCP различает ошибки аргументов и операционные ошибки.
- Сверены `Application.callLater/getMainThread`, `QtApplication.functionEvent`, методы ContainerStack/InstanceContainer/DefinitionContainer, userChanges и определение layer_height. Явного расхождения с выбранным способом интеграции не найдено.

## Что ещё требуется

1. Установить плагин в конфигурацию, загрузить Extension, зафиксировать версию приложения.
2. На Hybrid 530 V5.2.4 в режиме 3D прочитать исходное значение, изменить, сравнить ответ/get/UI.
3. Восстановить исходное значение и подтвердить get/UI; проверить неверное значение и область.
4. Сохранить реальные ответы/скриншоты и дополнить отчёт исполнителя. При сбое сначала исправлять его, затем повторять нужный сценарий.

Инструкция и PowerShell-команды уже есть в `plugin/README.md`. Следующий шаг пользователя: установка/запуск плагина и сообщение о наличии меню и адресе чата. Новый слайсинг, физическая печать или LLM для этого не нужны.

При первоначальном ревью в корневом README и архитектурных заметках оставались описания первоначального каркаса. **Исправлено при подготовке документации после runtime-приёмки:** текущая реализация ограничена глобальным layer_height через MCP, результат реального прогона отражён отдельно. ## Организация проверок

Unit-тесты на собственную логику остаются обязанностью разработчика. Отдельный чат ради дополнительных простых unit-тестов сейчас не нужен. Ведущий проверяет diff и достаточность проверок; пользователь или участник QA независимо выполняет реальные сценарии, сохраняет результаты и воспроизводит ошибки.

Новый QA-чат можно подключить позже для независимой проверки сценариев, установки и регрессий, если это освобождает время команды. Создавать его автоматически и дублировать существующие тесты не требуется. В общей папке один исполнитель меняет runtime-код за раз.
