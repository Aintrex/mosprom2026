# Заметки к будущей 5D-нарезке

23.10.2026. Исследование ведущего во время ТЗ 09. **Это чтение исходников, не реализация и не native-приёмка.** Работающий наблюдатель slicing.py пока допускает только classic; переключение трёх режимов уже существует отдельно. Следующее ТЗ по этим заметкам не назначено.

## Соответствие режимов

Подтверждено по `plugins/*/__init__.py` и `steslicer/BackendManager/BackendManager.py` выданного STE-Slicer-master:

| Режим кейса | Зарегистрированный backend |
| --- | --- |
| classic | CuraEngineBackend |
| cylindrical (5D Spiral) | CLIParserBackend |
| cylindrical_full (5D) | CylindricalBackend |

Нельзя выбирать backend только по похожему названию класса. Проверять `getBackendByType(mode)` и фактический `getCurrentBackend()`; другие режимы форка не добавлять.

## Что различается

- CLIParserBackend запускает StartSliceJob, внешний Glicer, ProcessCliJob, затем передаёт результат парсеру CLI. Итоговый `_onSlicingFinishedMessage` объявляет Done до замены placeholder в G-code и до сброса `_slicing`/платформы. Подтверждение должно происходить отложенно после окончания нативного callback, как в classic.
- CylindricalBackend — составной конвейер: StartSliceJob → GenerateBasementJob → CuraEngine → Glicer/ProcessCliJob → CLIParser. `_onSlicingFinishedMessage` после Cura — **промежуточный этап**: он выдаёт Processing/0.5 и запускает Glicer. Финал — `_onCliParserFinishedMessage`, также с Done до завершающей обработки списка/сброса флагов. Промежуточный G-code не экспортировать как законченный.
- Оба пути имеют `_process_cli_job`. CLIParserBackend **не имеет** `_generate_basement_job`, тогда как CuraEngineBackend и CylindricalBackend имеют. Обнаруженное прямое обращение общего backend_busy к отсутствующему полю передано исполнителю как исправление границы ТЗ 08. Нельзя заменить его молчаливым признанием любого неизвестного backend свободным.
- CylindricalBackend штатно переназначает handlers подчинённых CuraEngineBackend/CLIParserBackend. Плагин не должен повторять эти переназначения или самостоятельно соединять этапы: запускать внешний штатный backend целиком.
- Оценки времени/материала могут приходить несколько раз и на разных стадиях. Источник, последняя полная оценка и передача в PrintInformation должны быть подтверждены для конкретного внешнего backend; существующую защиту от чужих оценок не отключать без проверки source-пути.
- ProcessCliJob ждёт процесс и передаёт имена CLI. Чтение его исходника не доказывает работоспособность установленного Glicer/активации. Ошибки процесса, отсутствующие файлы и отсутствие финального сигнала должны давать честную ошибку/timeout, не синтетический успех.

## Что потребуется перед следующим заданием

Сверить конструкторы/ошибки/сигналы всех стадий, окончательную принадлежность gcode_dict текущему запуску, занятость подготовки и post-processing, readback PrintInformation и существующий native экспорт. Сохранять единую машину/платформу/режим/настройки и старую инвалидацию. Значение printing_mode в статусе/результате должно стать захваченным режимом запуска, а не строкой classic.

Расширение нельзя свести к удалению classic-guard: нужны проверки многоэтапного завершения и ошибок, затем настоящие прогоны обоих 5D на выданных моделях, Preview и повторное открытие 3MF. Не генерировать траектории моделью, не подменять файлы и не обходить активацию.

Дополнительно проверен ThreeMFWorkspaceWriter: в `SteSlicer/preferences.cfg` он переносит четыре заданных preference (`general/visible_settings`, `physics/automatic_drop_down`, `steslicer/active_mode`, `steslicer/categories_expanded`), а не все Preferences приложения. Ключ плагина в этот список не входит. Перед реальной сдачей всё равно проверяется фактически сохранённый проект установленной сборки; менять writer ради предположения об утечке не нужно.
