## Архив, порядок операций и закрытие

Путь подтверждён по `UM/Resources.py:getDataStoragePath` выданного Uranium. Constructor Extension работает наQt; получает строку `.../ai_assistant/chats`, не вшивает путь этой машины. Создание папки/чтение/валидация/сериализация/запись выполняются в одном файловом worker. Под ServiceLock берётся ограниченный plain-data снимок и ставится в очередь; I/O и ожидание файлового результата не держат ServiceLock/Qt. Список использует метаданные, отдельный GET читает нужный разговор, не загружая весь архив в LLM. Посещённые сессии остаются в ограниченном RAM-состоянии процесса для сохранения действующей идемпотентности; размер RAM выше размера JSON.

ВерсияJSON1, `session_<uuid>.json` и производный `index.json`. До20 диалогов,100 архивных сообщений/текстовых итогов,512КиБ на разговор,10МиБ суммарно с резервом16КиБ под индекс. Обрезка старой части явно помечается history_truncated; превышение байтов/числа/общего объёма не заменяет старый файл пустым. Временно для atomic replace требуется ещё место под один файл до512КиБ. Посторонние файлы/сохранённая копия повреждённого индекса учитываются при допуске новых записей.

Revision монотонно увеличивается при изменении RAM-истории. В очереди не более одного ожидающего снимка на чат, новый заменяет старый; последовательный writer проверяет актуальность. `saved_revision` подтверждается после записи файла и индекса, а не при принятии202 или завершении LLM. Temp в той же папке → flush/close → os.replace; при обработанной ошибке temp очищается. Прерванный запрос сохраняется как interrupted, после восстановления видна заметка. Повреждённые/неподдержанные chat-файлы остаются без изменений; индекс восстанавливается из валидных записей, повреждённая копия сохраняется отдельно. Ошибки видны в list/persistence, без содержимого/путей.

DELETE ставит tombstone и дожидается файлового подтверждения в HTTP worker. Поздний queued save/finish не возвращает удалённый чат. По замечанию ведущего отдельно закрыта гонка lazy-load: после load под ServiceLock повторно проверяются deleted/_deleting перед вставкой в RAM. Детерминированный тест задерживает GET после чтения, завершает DELETE и продолжает GET: ответ404, нет RAM/файла/строки списка. Ошибка удаления не повторяется автоматически; явно повторить удаление после выяснения состояния можно. История не удаляет пользовательский3MF/G-code и не отменяет engine.

Close Extension приходит наQt. Сервис фиксирует финальный снимок/stop и возвращается; новый дисковый join наQt не добавлен. Non-daemon cleanup helper внеQt даёт до2с на завершение worker. Проверены быстрый возврат при заблокированном I/O и обычный выход отдельного тестового Python-процесса с записью конечной revision. Это не гарантия при аварии ОС/зависшем диске: последняя неподтверждённая revision может потеряться; fsync и одновременная работа нескольких STE с одним архивом не заявляются. Уже подтверждённая revision к моменту ack записана. Реальное закрытие STE с этой версией ещё проверяется отдельно.

## Контекст и интерфейс

Whitelist архива содержит тексты/даты/название и безопасные краткие итоги инструментов/завершения slice/export. Известный ключ санитизируется также в user/assistant/title; Preferences/auth/rawproviderrequest, содержимое вложений/base64, пути, operational IDs/живые ссылки и произвольные объекты сервиса не сериализуются. Это локальный JSON без шифрования, не универсальная система распознавания любых неизвестных секретов.

По согласованию ведущего после рестарта восстанавливается **текстовая историческая справка**, до12 ограниченных блоков выбранного разговора. Детали прежнего tool-протокола сохраняются неполно: raw tool_calls/results/arguments/_attachment_ids не восстанавливаются, orphan tool results невозможны. Другие разговоры в LLM не подмешиваются. Старые model/slice/export/artifact/file/download IDs удалены из действующего восстановленного текста; ownership/observer/nativejobs/client ledger не оживают. Историческое вложение содержит только имя/expired, загружается заново. Сцена общая для разговоров, JSON истории не заменяет3MF.

Открытие разговора не вызывает LLM/tools. Объяснительный запрос после восстановления тоже не вызывает автоматическое чтение. Перед первым новым изменением нужны успешные get_slicer_state/list_models в том же ходе; до них guard возвращает history_refresh_required, stage=preflight/executed=false. Успех изменения снимает этот начальный guard, прежние требования чтения актуальных настроек/ID продолжают действовать. Лимиты8LLM/16tools/120s/30s, запрет повторов после неизвестного исполнения и единый реестр сохранены. Причины реальной LLM latency не исправлялись.

GETlist/snapshot/polling доступны при busy, глобального selected-session на сервере нет. Прежний API создания пустого дескриптора при busy сохранён: он не меняет сцену. DELETE защищён active-turn/собственной наблюдаемой slice/export. В UI Новый/выбор/удаление/отправка заблокированы при active/pending/своей наблюдаемой операции. Список — сворачиваемый details с названиями/датами, текущий выделен; обычные кнопки работают с Tab, длинный текст переносится. DOM-Markdown, закрытые JSONdetails, текущие upload/progress/downloads сохранены.

Process_id есть в status/snapshot/events. При смене процесса даже в прежней вкладке и при совпадении курсора выполняется GETrestore: старые карточки/вложения/попытки очищаются, сообщение автоматически не POSTится. Generation отсекает поздний polling другого чата; поздний ответ старой отправки не очищает новую. Истёкший pending обозначается явно. В том же процессе ручной повтор использует прежний body/client_message_id, без повторного upload. Saved показывается только после ack; загрузка/пустой список/ошибка/неполный архив/temporary различаются. Dev по умолчанию остаётся RAM, не пишет в AppData.
