# План нашей роли: интеграция STE Slicer

## Договорённость

Наша зона — роль №1: Extension, доступ к API слайсера, настройки/профили, сцена, режимы, слайсинг и экспорт. Этот чат ведёт анализ, задания и приёмку; отдельный чат исполнитель реализует очередное ТЗ. Пользователь проверяет поведение в установленной сборке и передаёт результаты между чатами.

Остальные участники команды и их роли здесь не назначаются. LLM, чат и HTTP остаются смежными частями продукта; изменения на границах согласовываем с их исполнителями. Для проверки нашего адаптера LLM не нужен: инструменты можно вызывать напрямую через существующий `/mcp`.

## К чему идём

Из запроса инструментов можно получить реальный настроенный проект и G-code на выданном STE Slicer. Все операции с приложением проходят через главный Qt-поток, результаты и ошибки доступны агенту, а в конце проверены три разрешённых режима и все выданные модели.

## Порядок работ

| Этап | Объём | Проверяемый результат |
| --- | --- | --- |
| 01. Первая реальная настройка | Запуск плагина, мост HTTP -> Qt, get/set глобального `layer_height`, фактический результат и ошибки | MCP читает значение, меняет его, повторное чтение и UI подтверждают изменение; прежнее значение восстановлено |
| 02. Машина, профили, режимы | Информация об активной машине, список и выбор качества/материалов, `printing_mode`; проверка фактического backend | На Hybrid 530 V5.2.4 выбираются нужные ID; три режима отражаются в настройках и BackendManager |
| 03. Загрузка модели | Загрузка локального файла через API, ожидание появления объекта, список, ID и габариты | Выданная модель появляется в сцене, её можно адресовать инструментом; загрузка не считается завершённой по одному возврату readLocalFile |
| 04. Слайсинг и файлы | Запуск, сигналы статуса/прогресса, время/материал, G-code, 3MF; сначала 3D, затем проба обоих 5D | Первый настоящий комплект project.3mf/result.gcode; проект повторно открыт, G-code проверен; ошибки лицензии/движка диагностируются |
| 05. Полнота инструментов | Расширение настроек и экструдера, создание/сохранение профилей, перемещение/поворот/масштаб, авторасстановка и удаление | Обязательные группы кейса покрыты реальными операциями; единицы измерения и ID согласованы |
| 06. Совместный сценарий | Подключение к агенту и событиям UI, последовательное исполнение операций, понятные ошибки | Реальный чат вызывает инструменты, видны изменения и прогресс, экспорт соответствует текущему завершённому слайсингу |
| 07. Приёмка и сдача | Все модели, три режима, новая установка, README и артефакты | На каждую модель есть проверенные 3MF/G-code/скриншоты; функции в README соответствуют проверенным |

Этапы 02–07 пока имеют только границы и критерии результата. Подробное ТЗ выдаём на следующий небольшой объём после отчёта по текущему. Если ранняя проверка покажет проблему с 5D, движком или писателями, исправление получает приоритет перед расширением инструментов.

## Как выдаём и принимаем задания

1. В этом чате формулируем цель, допустимые файлы, контракт и критерии приёмки. При необходимости уточняем API по исходникам.
2. Пользователь передаёт ТЗ отдельному чату в том же проекте. Достаточно ссылки/пути к файлу; исполнитель читает `AGENTS.md` и ТЗ.
3. Одновременно только один исполнитель меняет нашу часть общей рабочей папки. Незавершённые чужие изменения не трогать. Новый чат не означает отдельную копию файлов.
4. Исполнитель реализует только текущий объём, проводит доступные проверки и возвращает отчёт по формату из ТЗ. Если runtime недоступен, явно отмечает ручные проверки как невыполненные.
5. Пользователь приносит сюда отчёт или ссылку на него. Я проверяю diff и доказательства, принимаю результат либо выдаю конкретные исправления.
6. По завершении этапа выдаём следующее ТЗ. Коммит, push и merge — только по отдельному разрешению пользователя; разрешение на прошлый коммит не распространяется автоматически на будущие.

## Зависимости от команды

- Для этапов 01–05 достаточно работающего плагина и прямых вызовов инструментов; отсутствие готового LLM/UI не должно блокировать эту проверку.
- Команде агента сообщить имена и схемы реальных инструментов, формат результата и ошибки. Реестр единый, отдельные реализации для LLM и MCP не создавать.
- Команде HTTP/UI сообщить формат статуса длительной операции, завершения и результата; согласовать его до подключения этапа 06.
- Для итоговой проверки нужны выданные модели с описаниями, активированная сборка для 5D и фактические требования к архиву.

## Готовность нашей части

Не достаточно успешных unit-проверок или сообщения «слайсинг запущен». Нужен воспроизводимый прогон в выданной сборке, фактические значения настроек/объекты/режим, завершённый слайсинг и сохранённые файлы. Журнал проверок должен отличать чтение исходников, проверки с подменами и реальный запуск.
