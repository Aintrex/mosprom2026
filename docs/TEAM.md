# Распределение работы: 3 разработчика + 1 участник с меньшим опытом

**Статус: за нашей работой пользователь закрепил роль №1 — интеграцию STE Slicer. Роли остальных участников пока являются предложением.**

В нашей зоне основной чат ведёт анализ API, пишет ТЗ и принимает результат; отдельный чат исполнитель реализует очередное задание. Пользователь проверяет поведение в приложении и передаёт отчёт на приёмку. План нашей части: [PLAN_SLICER.md](PLAN_SLICER.md); первое задание: [TASK_01_SLICER_SETTINGS.md](tasks/TASK_01_SLICER_SETTINGS.md).

Роли можно поменять по сильным сторонам. Самому уверенному в Python/Qt стоит взять интеграцию со слайсером: это основная техническая неопределённость.

| Кто | Ответственность | Каталоги | Первый проверяемый результат |
| --- | --- | --- | --- |
| Разработчик 1: Python/Qt, интегратор | API STE Slicer, очередь в главный поток, настройки/профили, сцена, три режима, backend и экспорт | `plugin/AIAssistant/slicer/`, `AIAssistant.py` | Плагин загружен; реальная настройка прочитана и изменена; модель нарезана вручную через адаптер |
| Разработчик 2: агент и backend | OpenAI Chat Completions, tool calling, JSON-RPC MCP, реестр и валидация инструментов, события, Preferences ключа | `plugin/AIAssistant/agent/` | Реальный LLM вызывает один инструмент, получает результат и объясняет изменение |
| Разработчик 3: frontend и HTTP | SPA, история, вложения, показ действий/ошибок, прогресс и результаты; HTTP-маршруты | `plugin/AIAssistant/web/`, `server.py` | Чат работает с backend, передаёт файл и показывает tool call и его результат |
| Участник 4: QA и продукт | Установка по README, активация по инструкции организаторов, каталог моделей и задач, ручные прогоны, скриншоты, дефекты, аудитория и аналоги, презентация, сбор сдачи | `docs/`, `results/` | Таблица всех моделей, воспроизводимый сценарий демонстрации, первые скриншоты и список дефектов |

Участник 4 не обязан писать сложный код. Важнее следить за сроками, проверять результат глазами пользователя и не дать команде забыть итоговые артефакты. Сильный разработчик помогает ему один раз настроить окружение и воспроизвести эталонный для команды сценарий.

## Как не мешать друг другу

- Один общий репозиторий плагина, отдельные ветки `codex/slicer`, `codex/agent`, `codex/web`, `codex/qa`.
- До начала работы согласовать формат результатов инструмента и событий в `ARCHITECTURE.md`.
- Разработчик 1 владеет Extension; разработчик 3 владеет HTTP-сервером. Изменения на границе согласовывать.
- Разработчик 2 добавляет инструмент в общий реестр после появления реализации адаптера; схема используется и MCP, и LLM.
- После каждого рабочего этапа интегрировать ветки и запускать один общий сценарий. Ветку `main` держать запускаемой.

## Этапы

1. **До первого чек-поинта:** установить сборку всем, распределить модули, показать каркас, сформулировать архитектуру и ограничения. Подготовить ссылку на репозиторий для личного кабинета.
2. **Первый сквозной сценарий:** модель -> реальный LLM -> настройка -> слайсинг -> 3MF/G-code -> объяснение и скриншот. Начать с 3D, но 5D проверять технически с самого начала.
3. **До второго/третьего чек-поинтов:** расширить инструменты, вложения и события; проверить все три режима, прогнать организаторские модели.
4. **До сдачи:** повторная установка на чистую конфигурацию, проверка каждого файла, ZIP и демонстрация. Оставить запас перед 25 октября, 10:00 МСК.
