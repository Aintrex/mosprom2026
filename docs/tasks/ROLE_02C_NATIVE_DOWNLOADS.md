# Роль2C: скачать настоящий результат экспорта

Статус: назначается24.10 после приёмки12 (286 Python+8 JS). Успешный fetch04:24МСК не выявил новых веток/параллельной реализации. Выполнить только этот объём; upload/attachments ролей2A/2B и native writers не переписывать.

## Один законченный сценарий

Агент получает `get_export_status` со своим завершённым native-артефактом; в чате появляется кнопка G-code/3MF. Нажатие скачивает именно опубликованный файл штатного writer. Незавершённый, неизвестный, исчезнувший или устаревший результат не становится доступным. Ошибка скачивания не запускает новый экспорт автоматически.

Никаких редизайнов, фонового engine-monitoring, новых slice/export pipelines, WebSocket, анализа геометрии или нового набора LLM tools. Сохранить Python3.5, один реестр/QtBridge, идемпотентность сообщений, cursor recovery, ключи в Preferences.

## Узкая граница с native

Сейчас `Exports.artifacts` содержит принятые native-файлы и `local_directory`; HTTP не читает этот приватный объект напрямую. Добавить небольшой внутренний resolver по `artifact_id` в Exports/adapter через прежний QtBridge. Только известный завершённый принятый экспорт, текущий `slice_id` через прежнюю проверку актуальности и доверенные path/name/size/kind. Возвращаемый внутри процесса путь не становится полем MCP/REST/событий или запросом LLM.

Не искать файл по имени клиента, не брать путь из tool-result/JSON, не повторять writer. Не делать I/O/streaming в Qt. Не держать AgentService lock во время ожидания QtBridge или чтения файла. Native published-файлы уже остаются в своей cache-папке; не копировать их в upload-хранилище и не вводить новый recursive cleanup. Проверить, что закрытие/очистка upload не удаляет экспорт во время передачи.

До реализации кратко подтвердить ведущему resolver и порядок регистрации/скачивания/close. Нужен маленький согласованный патч native-границы, а не доступ server→adapter._exports.

## HTTP и события

- После фактического completed/valid и подтверждения resolver зарегистрировать download-ID. Один artifact_id получает стабильные `file_id` и относительный `download_url` вида `/api/files/{file_id}`. Повторный status/event не создаёт дубликаты и не меняет байты.
- Дополнить существующую карточку artifact в событии/снимке, сохранив native `artifact_id`, slice_id, имя, размер, kind/source/writer. Исходные upload-ID не выдавать как export downloads. Не менять upload-метаданные и лимиты.
- `GET /api/files/{file_id}`: только известный зарегистрированный экспорт. Перед открытием повторно проверить native-актуальность resolver, затем вне Qt безопасно открыть именно доверенный обычный файл, проверить размер/принадлежность и передавать ограниченными блоками. Не читать файл целиком в память. HTTP не принимает локальных путей и `?path`.
- Content-Type по реальному типу (`model/3mf`, для G-code допустим attachment application/octet-stream), Content-Length, безопасный Content-Disposition attachment, no-store/nosniff. Host/Origin и loopback остаются прежними. Заголовки/имя не должны позволять CRLF/path injection. Range/retry-stream/proxy поддержку не добавлять ради этого этапа.
- Неизвестный ID/исчезнувший файл —404; stale —409; закрытие сервиса/недоступный Qt —503 с понятным JSON до отправки тела. Если соединение оборвалось после начала потока, закрыть свой handle; не пытаться дописать JSON в бинарный ответ.
- `capabilities.downloads=true` только для реализованного resolver→HTTP пути; dev-режим не должен обещать native-готовность по одному флагу. Background_slice_events остаётся false.

## Минимальный UI

Показать список полученных артефактов и кнопку/ссылку только при рабочем относительном download_url и известном valid. Исторический artifact_ready без URL остаётся понятным локальным результатом, а не фальшивой ссылкой. Имя через textContent, href только собственного допустимого маршрута. Восстановить карточки из snapshot при refresh/410 и не дублировать их при повторном событии. Известную неактуальность после изменения сцены/настроек отобразить; сервер всё равно проверяет при GET. Полный дизайн принадлежит фронтендеру.
