# Сетевой timeout: безопасная диагностика для повторной приёмки

24.10.2026. Пользователь просит дальнейшие доработки и честный статус перед презентацией. Исходная проблема: реальный ход после get_setting/describe_settings завершился network_timeout. Исправление аргументов уже опубликовано в17b70f2; причина задержки провайдера не установлена.

## Узкий результат

Проверить текущий transport/service и сделать отказ понятным для повторного пользовательского прогона: на каком LLM-обращении истёк бюджет, сколько времени ожидали и какой бюджет был предоставлен, были ли до него подтверждённые изменяющие вызовы. Пользователь должен отличать отсутствие ответа LLM от отказа инструмента и неизвестного исхода native-операции. Сохранять текущие результаты после таймаута; повтор запроса не должен незаметно повторять запись.

Предпочесть минимальные дополнения к существующим ошибкам/их отображению; не строить систему телеметрии, журнал всех запросов, новый endpoint или диагностический UI. Вначале сообщить конкретную границу изменения. Если существующего error.message достаточно для числовых сведений — использовать его, не добавлять структуру ради структуры. Дополнительные поля согласовать в контракте, если они всё же необходимы.

## Ограничения

- Python3.5/api5, прежний transport/реестр/QtBridge/worker. Сетевой вызов вне Qt.
- Не менять30с/120с/8шагов/16tools наугад, не вводить retry, не запускать native повторно.
- Не обещать, что диагностика устраняет задержку. Размер схем/истории не объявлять доказанной причиной. Не менять набор tools/describe_settings без отдельного основания.
- Только счётчики/время/фиксированные коды и названия инструментов. Никаких ключей/URL с реквизитами, headers, response body, raw prompts, имён/байтов вложений, локальных путей или сырых provider exceptions в UI/логах. Для очередного запроса не логировать payload.
- Не читать Preferences/ключ пользователя и не обращаться к настоящему LLM/STE. Native-поведение проверяет пользователь.
- Уже завершённые native-изменения не отменять. Поздний сетевой ответ не принимать и не запускать по нему tools. Отказ до сети/неизвестный исход операции не маркировать как успешный или отменённый engine.
- Frozen296/manifest, TESTING_STEP_BY_STEP.md и manual_acceptance.ps1 не менять. AppData/установка/Git/принтер/новые чаты не входят в задание. Предыдущее разрешение публикации использовано коммитом17b70f2; новых commit/push не делать.

## Приёмка

Использовать существующие тестовые провайдеры/часы. Проверить meaningful-сценарии: timeout до инструмента без записей; timeout после подтверждённой записи с сохранением результата/без повторов; поздний ответ игнорируется; сведения об отказе не содержат ключа/пользовательских данных. Учитывать отличия remaining turn budget и per-call timeout. Не писать тесты только на текст сообщения и не расширять весь набор без причины.
