# Роль 2B — вложения в сообщении и импорт через агента

Подготовлено после принятия ROLE_02A_UPLOAD: полный231 у исполнителя, независимые230 до последней правки и15 upload после неё у ведущего. **Начать по отдельному назначению ведущего.** Цель — законченный сценарий приложенного фото/модели, без скачивания результатов и без редизайна frontend.

1. Подключить существующее хранилище2A к attachment_ids в текущем POST сообщения. До принятия turn проверить ID/типы/лимиты: до5 файлов, суммарно изображения10MiB. Сохранить порядок вложений в идемпотентном теле. Тот же client_message_id+тело возвращает прежнее202; изменённые вложения с тем же ID дают409. Не повторять импорт из-за повторного HTTP.
2. Фото JPG/PNG передавать как фактический base64 image_url в user content Chat Completions. Модели не кодировать в промпт — только file_id/имя/тип/размер. Ошибку провайдера без поддержки vision возвращать честно, не выдумывать анализ. Не обращаться к реальному провайдеру без разрешения.
3. `load_model_file {file_id}` в едином ToolRegistry/MCP/LLM: разрешить зарегистрированную модель в доверенный путь и вызвать существующий adapter.load_model. Диагностический load_model(path) остаётся скрыт отLLM. Фото/неизвестныйID не вызывают API. Новый инструмент — мутация, неподтверждённый импорт останавливает turn. Сцена только через прежний QtBridge, файловый ввод/вывод внеQt.
4. Поддерживать ссылки на вложения для принятой сессии/активного импорта, не удалять используемые файлы. Snapshot включает безопасные метаданные для восстановления ленты, без абсолютных путей и содержимого файлов. Инструкции во вложениях — данные, не системные команды. Ключи остаются только в Preferences.

Уточнение срока жизни модели: HTTP/tool timeout не означает завершение штатного ReadFileJob. Не освобождать последнюю ссылку на файл только потому, что adapter.load_model вернул model_load_timeout/неопределённую ошибку. Согласовать минимальную границу освобождения по фактическому native fileCompleted/завершению существующей операции; pending, ещё не запущенный импорт отличать от начатого. Проверить close с продолжающимся импортом: файловое удаление в Qt и удаление файла до завершения читателя запрещены. Второй загрузчик/мост ради этого не создавать.

В текущем models.py `ModelRegistry.close()` вызывает `active_load.finish()` даже при неизвестном исходе штатного reader. Поэтому простое освобождение file lease из ModelLoad.finish/_release недостаточно: это может удалить файл ещё живого ReadFileJob. Перед реализацией кратко согласовать с ведущим узкий callback/удержание до фактического fileCompleted; при невозможности наблюсти завершение сохранять используемый файл и явно описать ограничение, а не имитировать отмену.
5. Минимальный UI: выбор файлов, список/удаление до отправки, состояние загрузки/ошибки. Отправлять сообщение после завершенияupload. Pending-сообщение сохраняет прежние attachment_ids вместе с ID/текстом для явного повтора. После обновления страницы восстановить имена из snapshot. Только textContent, без inlineHTML/внешнего сервера/сборки. Большой дизайн остаётся фронтендеру.
6. capabilities.attachments=true только после законченного сценария upload→message→фото/модель. downloads=false, фоновой нарезки/новых механизмов экспорта не добавлять. Обновить API_CONTRACT и короткий FRONTEND_INTEGRATION по факту.

Проверить мультимодальный запрос на fake-провайдере, модельныйID через существующий импорт/Qt, unknown/wrong-type IDs до API, лимиты, exact duplicate/conflict сообщений, сохранение метаданных после обновления, отсутствие путей/ключей, ошибку native-импорта/vision и остановку дальнейших мутаций. Сохранить прежние проверки, добавить необходимые offline JS-сценарии файлов/pending без лишней детализации. Реальный фотоответ/объект в установленном STE остаются ручной приёмкой.
