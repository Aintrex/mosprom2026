Обновление статуса25.10: реализация и дополнение корзин завершены. После анализа пользователь отдельно разрешил ведущему обновить main и опубликовать текущий UI с тестами/документами. Ниже сохранены исходные ограничения исполнителя на этапе разработки. Два известных P2 — в UI_CHAT_REDESIGN_REVIEW.md.

Статус: поручение фронтендеру от25.10.2026. Реализовать локально и остановиться для проверки пользователем. **Не делать git add/commit/push/merge, не переключать ветки, не устанавливать плагин.** Постоянная автоматизация ведущего удалена по просьбе пользователя; это одно конкретное задание, а не новый монитор.

## Цель и исходная ситуация

Сделать спокойный, понятный чат для начинающего пользователя STE Slicer. Главный экран — переписка, файлы и ввод. Текущие действия, сохранение диалогов, управление сценой и скачивание должны остаться рабочими.

Замечания пользователя по трём скриншотам:

1. При длинном тексте и длинном слове поле ввода растёт/сдвигает кнопку «Отправить»; требуется устойчивая компоновка.
2. Каждый вызов инструмента выглядит отдельной большой карточкой, повторяются служебные сообщения. Они вытесняют человеческий ответ и мешают читать диалог.
3. Выходные G-code/3MF представлены громоздкими зелёными полосами над вводом. Нужны понятные сообщения с файлами. Пользователь также просит аккуратнее оформить прикрепляемые файлы.
4. В левой панели много разнородной информации. Оставить там диалоги и быстрые команды ниже; кнопку нового диалога поставить над списком.

Сначала прочитать **AGENTS.md**, актуальные **docs/API_CONTRACT.md**, **docs/FRONTEND_INTEGRATION.md**, существующие web/index.html/app.js/style.css и tests/test_agent_web.js. Старые числа лимитов в описательных документах сверять с актуальным API/кодом: этот этап не меняет лимиты или backend. Историческое TASK_UI_FILES_AND_MODEL_CONTROLS уже частично реализовано; не выполнять его заново целиком.

## 1 Компоновка

Предлагаемая структура экрана:

```text
STE Slicer AI         Короткий статус          Состояние / Модели / Настройки
┌──────────────────┬────────────────────────────────────────────────────┐
│ + Новый диалог   │ Название текущего диалога · статус сохранения      │
│ Диалоги          │                                                    │
│ ● Кронштейн      │ Сообщение пользователя + его вложения              │
│   Колесо         │ ▸ Действия ассистента: 6 завершены                 │
│   ...            │ Понятный ответ ассистента                          │
│                  │ Файлы готовы: G-code / Проект 3MF · Скачать        │
│ Быстрые команды │                                                    │
│ [Прочитать слой] │ Выбранные вложения                                 │
│ [Состояние STE]  │ [Скрепка] [Поле сообщения                 ] [→]   │
└──────────────────┴────────────────────────────────────────────────────┘
```

- Левый столбец: одна кнопка **«Новый диалог»**, список с названиями/выбранным чатом/датой, затем компактные **«Быстрые команды»**. Создание не дублировать в двух местах. Текущую btn-new-session можно перенести; одинаковых DOM-ID не делать.
- Список диалогов должен использовать большую часть панели и прокручиваться независимо. Быстрые команды остаются доступны ниже; на малой высоте их можно свернуть. Не закреплять десяток кнопок ценой почти исчезнувшего списка.
- Названия переносить/обрезать аккуратно; полное название доступно при выборе/фокусе. Сохранить создание/открытие/удаление с подтверждением и защищённое переключение. Удаление можно поместить в компактное меню строки; не удалять по одному случайному нажатию.
- Машину, режим и LLM показывать коротко в верхней части. Детали подключения/нарезки и текущие контролы моделей перенести в доступную по кнопке раскрываемую область/боковую панель. Они не должны занимать постоянную левую колонку или исчезнуть из продукта. Все кнопки должны открывать реальный блок, без декоративных неработающих элементов.
- На360–390px левая панель становится выдвижной/сворачиваемой, диалог и ввод остаются главным содержимым. Продумать закрытие и возвращение фокуса.

## 2 Сообщения и действия ассистента

- Сохранить различие пользователя/ассистента, читаемый Markdown: жирный текст, списки, абзацы, код, ссылки в рамках существующей защиты. Длинный текст не растягивает страницу.
- Вместо десятка больших карточек сделать **один блок «Действия ассистента» на ход**. По умолчанию он свёрнут. Во время выполнения: «Настраиваю печать · выполнено3 действия», только если события это подтверждают. После: «Действия ассистента · 6 завершено» или «4 завершено, 1 ошибка». Названия и числа — из фактических событий, не из предположений.
- В раскрытом блоке компактный список шагов: прочитанные значения, изменения before→after, единицы, состояние. JSON, схемы, служебные ID и сведения о разборе строк — во вложенных закрытых **«Технических деталях»**. Не повторять один и тот же служебный абзац под каждым параметром. Факт нормализации допустимо показать одной короткой заметкой с доступными подробностями.
- Пример человеческого шага: **«Заполнение:40% →100%. Значение проверено в слайсере»** — только при подтверждённом readback. Понятные названия enum брать из доступных данных/нынешних отображений; неизвестные значения не переводить наугад.
- **Не скрывать ошибку или неизвестный исход внутри закрытого блока.** В основной ленте остаётся краткое сообщение: что не получилось, подтверждено ли изменение, что можно проверить. Блок действий показывает соответствующий значок/счётчик; успешные шаги не делают общий результат зелёным при незавершённом/ошибочном.
- `validation/executed=false`: действие не запускалось. Timeout/неизвестный исход: результат не подтверждён, требуется чтение состояния. Stale, stopped, observation interrupted, invalid, pending и native failed различаются. Без автоповтора и без фиктивной кнопки Stop, если нет поддержанного API.
- Это **журнал фактических действий**, не «внутренние мысли» LLM. Не генерировать рассуждения, выдуманные этапы или объяснения причины сбоя. Не показывать пользователю chain-of-thought.
- Группировать по существующим turn_id/tool_call_id; при неполных/исторических данных показывать честный отдельный блок. Не объединять разные ходы по близости времени. Snapshot/refresh/410 восстанавливают ту же структуру без дублей и повторных POST.

## 3 Ввод сообщения

- Один устойчивый composer в нижней части чата. Скрепка, textarea и отправка имеют собственные колонки; текст не вытесняет и не сжимает кнопку. Кнопка не становится второй строкой и не закрывает ввод.
- Textarea плавно растёт от1 до примерно6 строк, затем прокручивается внутри; разумная максимальная высота около160px на обычном экране, на телефоне учитывать доступную высоту. Не увеличивать её бесконечно по scrollHeight. После отправки очищать и возвращать исходную высоту.
- Перенос длинного слова/ссылки/пути и1000 символов без пробелов, без горизонтального переполнения. Проверить min-width:0, wrap и ограничения колонок/высоты. При необходимости компактная кнопка-иконка отправки имеет доступное имя «Отправить» и подсказку.
- Enter отправляет, Shift+Enter добавляет строку; IME/composition не отправляется преждевременно. Сохранить ограничения maxlength, pending/busy/uploads, доступность кнопок и точное тело повторной разрешённой отправки. Не терять текст и список файлов при ошибке.
- Краткая подсказка под вводом, подробные лимиты доступны рядом с выбором файлов. Длинная строка лимитов не должна вытеснять чат. Не маскировать ошибку валидации placeholder-текстом.

## 4 Вложения и результаты файлами

**До отправки:** компактные карточки/чипы с иконкой формата либо миниатюрой фото, именем, человеческим размером, статусом загрузки, кнопкой удаления с понятным названием. Длинное имя не ломает сетку; полное имя доступно. Обрабатывать загружается/готово/ошибка; ошибка файла объясняется рядом. Использовать фактические лимиты /api/status.

**После отправки:** вложения находятся рядом с сообщением пользователя как часть этого сообщения. Успешная загрузка файла и импорт в сцену — разные события. «Добавлено в сцену» писать только после успешного load_model_file; не утверждать импорт по одному upload201/сообщению пользователя. Историческое вложение без действующего ID честно недоступно и требует повторного прикрепления. Миниатюры не восстанавливать из произвольного локального пути; blob URL освобождать.

**Результаты:** убрать постоянно растущий список artifacts из composer. Показывать в ленте компактное сообщение **«Файлы готовы»** с одной/двумя строками:

```text
G-code             result.gcode    2,0МБ    [Скачать]
Проект STE         project.3mf     110КБ    [Скачать]
```

- На телефоне строки складываются вертикально. Это выходные файлы, не вложения пользователя. Техническая информация/slice_id остаются по раскрытию; размер форматируется, а не пишется огромным числом байтов.
- Связывать файлы с ходом/операцией только по доступным данным. Не приписывать общий artifact текущему чату или последнему сообщению без основания. При отсутствии связи — отдельное сообщение результатов в текущей фактической ленте, с техническими сведениями.
- Дедупликация/обновление по artifact_id: повтор события не создаёт новую карточку. После snapshot/refresh карточки восстанавливаются. Известный stale убирает ссылку и показывает «Устарел — требуется новая нарезка»; исчезнувший файл/404/409/503 не получает успешную отметку.
- Скачать доступно только по уже существующему разрешённому download_url и valid===true, с прежней whitelist URL/повторной серверной проверкой. Не загружать целиком G-code в JS ради кнопки, не создавать экспорт повторно, не формировать ссылку из имени файла/пути. Нарезка completed не равна writer completed/artifact_ready.

## 5 Стиль и границы реализации

Светлый спокойный интерфейс с синим акцентом, читаемая системная типографика (обычный текст примерно14–16px), единые отступы/радиусы/состояния. Избавиться от одинаково зелёных больших полос; цвет дополнять текстом/значком. Видимый focus, клавиатурное управление раскрытиями и меню, подписи и доступные имена. Прокрутка ленты не должна прыгать вниз, когда пользователь читает старые сообщения; новые события дают понятный переход к низу.

Основной объём: **plugin/AIAssistant/web/index.html, app.js, style.css**, адресные UI-тесты и отчёт. Обычные HTML/CSS/JS, stdlib/backend/Qt/реестр/tools не перерабатывать. Без React/Vite/npm-сборки/CDN/новой библиотеки Markdown/внешних шрифтов, обязательной Figma и неподдержанных REST-путей. Если для связи данных не хватает контракта — сначала описать конкретный пробел ведущему, не додумывать ID/успех.

Сохранить DOM-безопасность: текст/имена/ошибки не идут в innerHTML, нынешний безопасный Markdown остаётся. HTTP/CSP/Host/Origin и проверка загрузок/скачиваний прежние; ключ LLM не вводится и не появляется в браузере. Сцену/режим/профили не менять ради демонстрации UI. Не вмешиваться в принятый фикс5D и OpenSCAD.

## 7 Уточнение пользователя после ручного просмотра

Убрать нижние кнопки **«Открыть»** и **«Удалить…»** под списком. Чат открывается нажатием на его название/строку, как сейчас. Справа **у каждого чата** добавить отдельную компактную кнопку с иконкой корзины, подсказкой и доступным именем «Удалить диалог …».

Корзина удаляет именно свой диалог по захваченному ID, после подтверждения с названием. Нажатие на неё не открывает чат и не меняет выбранный диалог. Не вкладывать button в button: строка-контейнер содержит отдельные кнопки открытия и удаления. Иконка доступна клавиатурой и на touch; не скрывать её исключительно в hover. Длинное название не вытесняет корзину.

Сохранить busy/pending/upload/switching guards и подтверждённое удаление через текущий DELETE. При ошибке/неизвестном исходе чат не исчезает и DELETE не повторяется. Удаление чужого чата сохраняет текущую переписку; удаление текущего очищает её только после подтверждения сервера. Убрать старые DOM-ID/ссылки/обработчики elOpen/elDelete так, чтобы реальный DOM не получал null-ошибок. Если кнопки списка оказались внутри новых обёрток, buttons() должен блокировать реальные кнопки, а не только обёртку.

Адаптировать существующие значимые JS-тесты удаления и добавить проверку конкретного ID/отсутствия побочного открытия, отмены подтверждения/отказа/блокировки. Проверить desktop/mobile и остановиться с дополнением UI_CHAT_REDESIGN_REPORT.md. Без commit/push; ранее сделанный новый интерфейс и документы ведущего сохранить.
