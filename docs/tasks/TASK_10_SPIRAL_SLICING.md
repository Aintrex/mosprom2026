# ТЗ 10 — штатная нарезка 5D Spiral

Подготовлено после ревью ТЗ09 (независимые216 тестов OK). **Начать по отдельному назначению ведущего.** Это расширение существующих slicing/exports, не новая реализация движка. Native-приёмка прежних этапов остаётся открытой.

## Цель и границы

После выбора cylindrical существующий start_slicing должен запустить штатный CLIParserBackend, статус — показать его фактическую работу, результат — свежие время/материал/G-code именно этого запуска. Штатные export_gcode/save_project_3mf сохраняют этот подтверждённый результат. Classic сохраняет прежнее поведение. Режим cylindrical_full требует отдельного разбора составного конвейера и в этом ТЗ по-прежнему отклоняется явной ошибкой.

Предварительные source-заметки: `docs/reports/FIVE_D_SOURCE_NOTES.md`. Самостоятельно повторно сверить выданную копию CLIParserBackend, его StartSliceJob/ProcessCliJob, steslicer/BackendManager, PrintInformation и writers. Не ориентироваться на современную Cura, не менять дистрибутив и не копировать внешний код целиком.

Внешние контракты прежние: start_slicing {}, get_slicing_status/result {slice_id}, export_gcode/save_project_3mf {slice_id}, get_export_status {export_id}; единый реестр инструментов, один общий guard. Не добавлять альтернативные имена/сервер/SPA/LLM-клиент. Названия backend брать из регистрации по режиму; нельзя считать cylindrical сокращением имени CylindricalBackend — это CLIParserBackend.

## Выполнение

1. До запуска проверить разрешённый режим (classic либо cylindrical), актуальную машину/платформу и соответствие current backend зарегистрированному getBackendByType(mode). Сохранить режим в контексте запуска. Поддержку runtime проверять по реальным API/layout, неизвестное отклонять до записи. Auto-slice пользователь выключает заранее; прочие прежние guards и запрет preview/нескольких непустых платформ сохранить.
2. Использовать forceSlice внешнего native backend целиком. Он запускает подготовку → Glicer → ProcessCliJob → CLIParser. Не запускать subprocess из плагина, не переназначать native message handlers, не собирать траектории самостоятельно и не обходить активацию.
3. Запуск, Glicer exit, ProcessCliJob.finished, progress=1 и итоговый Done — разные события. Признавать completed только после финального native callback, свежего собственного G-code и подтверждения выхода всех стадий. CLI выдаёт Done до окончания собственной завершающей обработки: нужен отложенный Qt-readback, а не немедленный успех из signal handler.
4. Учесть backend_busy с _process_cli_job/_glicer_process вместо отсутствующего у CLI basement. Ошибки start job, ProcessCliJob, процесса, Arcus/parser, отмена и отсутствие финала должны давать честную ошибку/timeout. Не освобождать guard по одному _slicing=false, пока известная стадия ещё работает. Подтвердить source-поведение завершившегося/ещё живого процесса и возможного переиспользования native процесса.
5. Сохранить привязку slice_id к собственному старту, native job, буферу gcode_dict, машине, сцене, режиму, платформе, геометрии и настройкам. Переиспользованный старый G-code/оценка, чужой запуск и смена режима не могут завершить текущий run успешно. Результат после изменения остаётся stale. Старый completed одного режима не становится результатом другого.
6. Время/материал брать из подтверждённой передачи текущего внешнего backend в PrintInformation. Проверить повторные оценки и порядок сигналов. Не снимать защиту от чужих оценок ради зелёного теста, не рассчитывать свои оценки. Отсутствующие показатели — null с явным предупреждением согласно прежнему контракту.
7. printing_mode статуса/результата — захваченный фактический режим, backend_id — реальная регистрация. Нельзя везде подставлять classic. Экспорт только свежего завершённого slice_id через существующие writers/WriteFileJob, с фактической проверкой файла и контекста; сохраняемый 3MF должен содержать cylindrical и выбранные настройки.
8. Timeout/shutdown не убивают native процесс и не дают автоматического повтора. Прежний бюджет остаётся ограниченным; зависшая стадия сохраняет блокировку изменений до реального выхода. Ошибки описывать без секретов, содержимого моделей и приватных путей.

Сначала исследовать и кратко сообщить ведущему найденные несовпадения протокола. Если исходники не позволяют достоверно наблюдать завершение, привести конкретную границу, не объявлять фиктивный completed. Не расширять задачу на cylindrical_full, профили, файлы чата или UI.

## Проверки и сдача

Сохранить актуальный прежний набор. Добавить проверки fork-shaped CLI без basement: полный цикл с несколькими стадиями, Done до последних изменений G-code, ошибки каждой стадии, промежуточный/чужой сигнал, live/dead process, итоговые оценки/режим/ID, старые буферы, mode change/stale, busy/timeout/late finish/shutdown, запуск и экспорт текущего результата. Classic должен сохранить все прежние проверки. Тесты с подменами явно так назвать; source-проба не равна установленному runtime.

Обновить API_CONTRACT/README/PLAN точечно, включая честный список поддержанных режимов нарезки. Подготовить TASK_10_REPORT.md с источниками, результатами проверок, ограничениями и ручными командами.

Native-сценарий после разрешённого обновления установленной копии: на Hybrid 530 V5.2.4 выбрать cylindrical, загрузить небольшую подходящую модель, зафиксировать настройки, запустить свой slice_id и дождаться финала, сохранить native G-code/3MF, проверить Preview и повторное открытие проекта. Отдельно повторить classic как регрессию. Отсутствие активации/движка или неподходящую модель записать как блокер ручного прогона, не обходить. Принтер не запускать.

Commit/push, установка, реальные LLM-запросы и следующий этап этим ТЗ не разрешены. После отчёта остановиться для ревью ведущего.
