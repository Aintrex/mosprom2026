# ТЗ 02: диагностика машины и переключение 3D/5D

Статус: готово к передаче исполнителю. ТЗ 01 принято в STE Slicer 7.10.12, Hybrid 530 V5.2.4, 3D; протокол — `docs/reports/TASK_01_RUNTIME.md`. Реализовать только это задание и вернуть отчёт. Это первая часть этапа 02 плана; профили и материалы будут отдельным объёмом.

## Цель

Получать фактическое состояние активной машины и переключать `classic`, `cylindrical`, `cylindrical_full` через API слайсера, подтверждая изменение настройки **и** выбранного backend. Для проверки не нужны LLM, новый UI, загрузка модели или слайсинг.

## 1. get_slicer_state

Аргументы `{}`, дополнительные поля запрещены. Все обращения к app/stack/manager выполняются в главном Qt-потоке. Успех — общий формат `ok/data`, пример:

```json
{
  "ok": true,
  "data": {
    "connected": true,
    "application_version": "7.10.12",
    "machine": {"id":"runtime-machine-id","name":"Stereotech Hybrid 530 V5.2.4","definition_id":"hte530v5.2.4"},
    "printing_mode": "classic",
    "backend": {"id":"CuraEngineBackend","expected_id":"CuraEngineBackend","matches_mode":true},
    "available_modes": [
      {"id":"classic","label":"3D","backend_available":true},
      {"id":"cylindrical","label":"5D Spiral","backend_available":true},
      {"id":"cylindrical_full","label":"5D","backend_available":true}
    ]
  }
}
```

ID/имя машины/definition_id/version/backend берутся из API, пример не является константами. expected_id — результат lookup текущего режима в менеджере. matches_mode подтверждает соответствие текущего backend ожидаемому runtime-объекту; сравнения только строкового значения printing_mode недостаточно.

При подключённом приложении без активной машины диагностика успешно возвращает connected=true, machine=null, printing_mode=null, backend=null, available_modes=[]; это не означает готовность к печати. При отсутствии app в dev-режиме — `slicer_not_connected`.

Если текущий режим не входит в три разрешённых, вернуть его фактическую строку и доступные диагностические сведения; не подменять его classic. available_modes перечисляет только три режима кейса. backend_available означает наличие регистрации, не работоспособность движка, лицензии или завершённый тест 5D. Отсутствующий expected/current backend обозначать null, matches_mode — false либо null, если нечего сопоставлять.

## 2. set_print_mode

Аргументы `{"mode":"classic"}`; enum из трёх значений, дополнительные поля запрещены. Неверный тип/режим/лишние поля — JSON-RPC `-32602` до изменения приложения.

Алгоритм:

1. На Qt-потоке проверить активную машину, определение printing_mode и поддержку запрошенного режима машиной. Для 5D проверить machine_five_axis и доступность enum. До записи проверить наличие `getBackendByType(target)`.
2. Сохранить исходный режим и реальный backend. Изменить `stack.userChanges` штатным API; не вызывать приватный `_onSettingChanged` и не устанавливать `_current_backend` вручную.
3. Дать event loop обработать штатные сигналы. ContainerStack.propertyChanged queued: backend может не смениться в том же callback, где выполнен setProperty.
4. Подтвердить фактическое значение printing_mode и соответствие `manager.getCurrentBackend()` результату `manager.getBackendByType(target)`.
5. Только после обоих подтверждений вернуть успех:

```json
{"ok":true,"data":{"before":"classic","after":"cylindrical","backend":{"id":"CLIParserBackend","expected_id":"CLIParserBackend","matches_mode":true}}}
```

Ожидание/повторные короткие проверки выполняются без блокировки Qt и с общим конечным бюджетом, ориентир 5 секунд, меньше HTTP timeout. Можно повторно использовать мост для коротких проверок из worker. Не запускать вложенный Qt event loop или `processEvents`, не делать sleep/Event.wait на Qt-потоке. Если прямой вызов из Qt-потока не поддерживает асинхронное подтверждение, завершать его явной ошибкой до записи, а не создавать deadlock.

Параллельные переключения не должны подтверждать результаты друг друга: сериализовать их вне Qt-потока простой блокировкой либо отклонять второе как `switch_in_progress`. Универсальная система jobs не нужна. До старта callback сохраняется отмена просроченной записи из ТЗ 01; после начатой записи состояние может быть изменено — при ошибке сообщить необходимость get_slicer_state, не обещать откат и не повторять запись автоматически.

Установка уже активного режима идемпотентна: вернуть подтверждённое состояние без лишней записи/перезапуска при совпадающем backend. Если строка режима совпала, а backend не соответствует, не возвращать ложный успех.

Ошибки операций: существующие `slicer_not_connected`, `no_active_machine`, `setting_unavailable`, `qt_timeout`, `slicer_error`; новые по необходимости `mode_unavailable`, `backend_unavailable`, `mode_not_applied`, `backend_not_switched`, `switch_in_progress`. Неудача режима не должна выдаваться как Unknown tool. MCP isError соответствует ok=false.

Не переключать режим во время заведомо активной операции слайсинга. Если в текущем объёме нет достоверного определения её состояния, явно описать ограничение и тестировать на пустой сцене; не выдумывать отсутствующий getState/isBusy и не заявлять такую защиту реализованной без проверки API.

## Проверки

Сохранить успешные проверки ТЗ 01 и добавить значимые сценарии:

- Диагностика версии/машины/режима, отсутствия машины, backend и dev-подключения; все чтения происходят на главном потоке.
- Три допустимых режима, неизвестные/alpha режимы и неверные аргументы, отсутствие поддержки/регистрации backend до записи.
- Смена строки настройки раньше backend: до обработки отложенного события успех не возвращается, после события корректно подтверждается. Подмена должна моделировать эту задержку, а не менять оба значения сразу.
- Настройка изменилась, backend не сменился — операционная ошибка и необходимость перечитать состояние, не успех.
- No-op без перезапуска при уже согласованном режиме/backend; таймаут, shutdown, параллельный вызов, отсутствие поздней записи после отмены.
- Общий tools/list/MCP; сохранение старых схем get/set и работа dev-сервера; совместимый с 3.5 синтаксис.

Не вводить обязательное количество тестов и не создавать тесты ради покрытия строк. Новые проверки должны отличать правильную реализацию от реального возможного дефекта.

## Ручная приёмка после реализации

Проводится отдельно с пользователем после обновления установленной копии. Сохранить проект, пустая сцена, машина Hybrid 530 V5.2.4. Прочитать get_slicer_state и исходный режим; по очереди проверить 3D -> 5D Spiral -> 5D -> исходный режим, сверяя UI и backend. Фиксировать реальные ID из диагностики, сообщения об отсутствующем backend/лицензии не скрывать. Наличие регистрации и переключение UI не доказывают готовность G-code; нарезка и экспорт будут другим заданием.

Во время этой приёмки не менять профиль качества/материал и не запускать физическую печать. Если runtime недоступен исполнителю, подготовить точные команды PowerShell, отметить ручной этап невыполненным и вернуть работу ведущему.
