## Этап A: прикрепление файлов

### Пользовательский сценарий

1. Прикрепить небольшой STL и PNG/JPG, написать: «Загрузи эту модель и объясни, что на фото».
2. В ленте видны имена вложений и фактические вызовы инструментов.
3. Фото передано провайдеру как `image_url` с base64; модель загружена существующим native-инструментом. Текстовый ответ не является доказательством загрузки — нужен подтверждённый результат инструмента и объект в STE.
4. Неизвестный файл, неверный формат или ошибка импорта дают понятную ошибку без повторного изменения сцены.

### Хранилище и HTTP

- Добавить `POST /api/files`: multipart/form-data, одно поле `file`, один файл. Ответ 201: `{"file_id":"file-...","name":"part.stl","kind":"model","size_bytes":1234,"mime_type":"model/stl"}`. Для JPG/PNG `kind` = `image`.
- `file_id` выдаёт сервер. Исходное имя — только для отображения; физическое имя генерировать внутри собственной папки временных вложений. Абсолютные пути не возвращать браузеру, модели и в событиях.
- Поддержать только JPG/JPEG, PNG, STL, OBJ, 3MF. Проверять расширение, допустимый тип и признаки содержимого; одной строке Content-Type клиента не доверять. Полную геометрическую корректность модели подтверждает читатель STE, свой конвертер моделей не писать.
- Стартовые технические лимиты: модель до 50 MiB, изображение до 5 MiB, до 5 вложений в сообщении, суммарно изображения до 10 MiB на сообщение. Это наши лимиты прототипа, не условие организаторов. Ограничивать также HTTP-обёртку и совокупное хранилище (например, 250 MiB на процесс); отдавать понятные 413/ошибки до обработки безграничного тела.
- Сохранить проверку Host/Origin, loopback и текущий список разрешённых статических файлов. Файлы отдавать отдельным обработчиком по ID; не добавлять папку загрузок в общую раздачу.
- Файлы создавать исключительно в своей папке, не разрешать перезапись, выход через имя/разделители/ссылки. Не распаковывать 3MF самостоятельно на произвольные пути. Обрабатывать повреждённые и чрезмерно раздувающиеся ZIP без неограниченного чтения.
- Реестр файлов должен безопасно обслуживать HTTP/agent-потоки. Удалять только собственные файлы; не удалять файл во время отправки, импорта или использования принятой сессией. После перезапуска неизвестные ID должны давать 404, а не доступ к произвольному пути.

### Агент и единый реестр инструментов

- Расширить существующее `attachment_ids` в POST сообщения. Проверять ID, тип и лимиты до принятия turn и до изменения сцены. Сохранить идемпотентность: тот же `client_message_id` и тело возвращают прежний ответ; изменённые вложения с тем же ID — 409. Повтор HTTP не должен повторять импорт.
- Изображения добавлять к пользовательскому сообщению Chat Completions как `image_url` с фактическим MIME и base64. Не добавлять бинарные STL/OBJ/3MF в текст запроса; для них передавать имя, ID, тип и размер.
- Добавить инструмент `load_model_file({"file_id":"file-..."})`: он разрешает только зарегистрированное модельное вложение и вызывает существующий `adapter.load_model()` с доверенным внутренним путём. Фото и неизвестный ID не должны вызывать импорт.
- Диагностический `load_model(path)` оставить недоступным LLM. Не разрешать модели выбирать локальный путь или выполнять Python.
- Использовать единственный ToolRegistry для MCP и LLM. `load_model_file` — мутация; ошибка или неподтверждённый результат останавливает текущий turn по существующим правилам. Не создавать второй каталог схем или новый мост Qt.
- Файловый ввод/вывод и сеть — вне Qt. Вызовы приложения — через существующий adapter/QtBridge. Инструкции внутри вложений считать данными, не системными командами.
- Ключ остаётся в Preferences, не появляется в файловом API, браузере или логах. При отсутствии поддержки изображений провайдером сообщать ошибку; не подменять её выдуманным анализом.

### Минимальный UI

Добавить выбор файлов, видимый список с удалением до отправки, состояние загрузки и ошибку. Отправлять сообщение после успешной загрузки выбранных файлов. Сохранять ID вложений вместе с pending-телом для безопасного повтора. Восстанавливать имена из серверного snapshot/метаданных. Показывать данные через textContent. Полный редизайн оставить участнику фронтенда.

## Этап B: скачивание настоящих 3MF/G-code

Native-экспорт уже существует: `export_gcode`, `save_project_3mf`, `get_export_status`. Сейчас события содержат `artifact_id`, имя, размер, источник, writer и slice_id; download_url пока нет.

- Регистрировать файл для скачивания только после фактического `completed` native-экспорта и подтверждения артефакта. Возвращать `file_id` и относительный `download_url` вида `/api/files/{file_id}` в карточке артефакта.
- `GET /api/files/{file_id}` отдаёт только известный файл с корректным Content-Type, размером и безопасным Content-Disposition. Никаких `?path=...`, произвольных абсолютных путей или чтения файлов из пользовательского JSON.
- Перед скачиванием проверить существование и актуальность зарегистрированного результата. Если файл исчез/срез устарел, вернуть понятные 404/409; не запускать новый экспорт незаметно.
- Нужна узкая граница с ролью 1: resolver зарегистрированного native `artifact_id` через существующий QtBridge возвращает доверенный путь, имя, размер и актуальность. **Не читать приватные `adapter._exports` из HTTP-потока.** Описание интерфейса/минимальный патч согласовать с ведущим после ТЗ 08. До этого не обещать готовые downloads.
- Использовать файл, созданный штатным writer. Не сочинять G-code, не собирать собственный ZIP вместо проекта и не выдавать тестовый файл за экспорт STE.
- Браузеру показывать кнопку скачивания только после появления рабочего URL. Старое событие artifact_ready без URL показывать как локально сохранённый результат.

## Границы работы и объединение

Основная зона роли 2: `server.py`, `agent/service.py`, `agent/llm.py`, новый модуль хранения файлов, минимальные элементы `web/`, соответствующие проверки и документация. Существующие сессии, курсоры событий и ограничение одного turn на сцену сохранить.

`slicer/`, общий `agent/tools.py` и его схемы сейчас меняет роль 1. Изменения на этой границе готовить небольшим отдельным патчем в своей ветке и передавать ведущему для объединения; не заменять файлы целиком старой версией. С фронтендером передать формы JSON/ошибок и согласовать UI-файлы до их изменения. Реализация не должна ждать большого редизайна.

Не включать сюда расстановку, 5D-нарезку, собственный анализ геометрии, новые профили, WebSocket, серверную БД или перенос приложения на современный Python. Сохранить Python 3.5, stdlib и текущую простую архитектуру.
