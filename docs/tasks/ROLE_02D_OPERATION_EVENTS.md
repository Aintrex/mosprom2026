# Роль2D: актуальный прогресс собственных операций

Назначено по прямому поручению пользователя24.10 продолжить вторую роль, пока он проверяет первую. База принята:296 Python/10 JS, роли2A/B/C не переписывать. Пользователь тестирует отдельную копию `tmp/acceptance/baseline_296/AIAssistant`, её и manifest не менять. Основной runtime меняет только «Разраб»; ведущий пишет подробную инструкцию/PowerShell helper.

## Проблема и результат

Сейчас чат обновляет slice/artifact только после tool-call в цикле LLM. Если ответ агента завершился или достигнут предел шага, engine/writer продолжает работу, а UI остаётся со старым снимком. Это незакрытая часть обязательного статуса/прогресса кейса.

После запуска через агента `start_slicing`, `export_gcode` или `save_project_3mf` соответствующая карточка обновляется до фактического результата без нового сообщения пользователя и без новых запросов LLM. Завершение ответа агента не завершает engine. Готовый экспорт получает прежнюю безопасную download-карточку автоматически после подтверждённого статуса. Observer никогда сам не запускает slicing/export и не повторяет мутацию.

## Минимальная реализация

- В AgentService один небольшой worker наблюдения на процесс, предпочтительно запускаемый лениво при первом принятом своём запуске. Не отдельный поток на сообщение/сессию и не новый framework/scheduler. Использовать threading/Event/прежний shutdown.
- Следить только за подтверждёнными ID собственных запусков, привязанными к сессии; не сканировать native-сцену/все исторические IDs. Одновременных native-запусков фактически мало: один активный slicing и один активный export в приложении. История не должна превращаться в32 независимых опроса каждую секунду.
- Читать прежние get_slicing_status/get_slicing_result/get_export_status через существующую безопасную границу ToolRegistry/adapter/QtBridge из worker. Не читать приватные backend/Exports из agent/server, не обращаться к Qt из HTTP/LLM-потока, не менять slicer pipeline/guard/timeout/writers.
- Polling примерно раз в секунду; результат собственного completed/valid подтверждать прежним result API, native ошибки/timeout/valid=false отображать честно. Не опрашивать бесконечно terminal-операции. Ошибка чтения не означает остановку engine; конечное backoff/сообщение «наблюдение прервано» без выдуманного completed/cancel и без нового start.
- При завершённом экспорте использовать принятый2C resolver/DownloadRegistry, без собственного доступа к файлам/нового download endpoint. Регистрация не держит ServiceLock во время Qt/I/O. Одинаковые статусы/готовые карточки не дублировать.
- Существующие события slice_progress/slice_finished/artifact_ready, snapshot/cursor/410 и безопасные поля сохраняются. Сам observer не создаёт фальшивые LLM tool_started/tool_finished. UI достаточно минимально объяснить автообновление и его границы; редизайн не входит.
- Учитывать гонку: поздний read старого ID не заменяет новую операцию/не оживляет stale после мутации. Захватывать ID/поколение под коротким ServiceLock, читать вне lock, перед публикацией повторно проверить владельца/поколение/closed. Тот же ID после known invalidation не становится снова valid лишь из-за старого ответа.
- Наблюдение продолжает работать при idle/ошибке/лимите LLM-turn; не делает LLM-запросов и не увеличивает лимиты цикла8/16/120. Прямой диагностический MCP и ручные действия UI не считать автоматически собственными запусками агента.
- Close прекращает новые чтения/публикацию; не join-ить ожидающий Qt worker на Qt-потоке. Поздний ответ после close не создаёт событий/карточек/новых запросов. Не менять жизненный цикл native engine и файлов; неизвестный исход остаётся неизвестным.
- capabilities.background_slice_events включать только после реализованного пути; dev без native не обещает подключение. Документировать также автоматическое наблюдение собственных export и отличие от копии296.

Сначала коротко сообщить ведущему конкретную схему одного worker, ownership/поколения и close, затем реализация только этого объёма. Без новых runtime-зависимостей/REST-маршрутов/WebSocket/хранилищ/очередной таблицы tools.

## Проверки и отчёт

Проверить значимое поведение: queued→running→completed и реальные оценки после idle; ошибка/timeout/stale; экспорт→download-ready без следующего LLM-call; дедупликация; старый read после мутации/нового ID; завершение LLM с ошибкой не останавливает наблюдение; ограниченный опрос terminal; shutdown с ожидающим Qt без публикации/зависшего join. Проверки с управляемыми Event/clock/ответами, без хрупких длительных sleep и реальных реквизитов. Сохранить296 Python+10 JS, границы fake/native явно указать.

Обновить API_CONTRACT/FRONTEND_INTEGRATION/короткий README по окончательному поведению и ROLE_02D_REPORT.md. Native-прогон/реальный провайдер пользователь проверяет отдельно. Не менять установленный плагин, snapshot296/manifest, docs/TESTING_STEP_BY_STEP.md и scripts/manual_acceptance.ps1 ведущего. Не выполнять Git/push/слияние/проверку удалённых веток, физическую печать или реальные LLM-запросы. После отчёта остановиться для ревью; следующих функций не назначено.
