# ТЗ 11 — штатная нарезка 5D

Подготовлено после принятия ТЗ10: независимые257 тестов OK, JS8 сохранены. **Начать по отдельному назначению ведущего.** Сохранить итоговый набор и обе части вложений2A/2B. Это последний разрешённый режим нарезки из кейса, а не новая система слайсинга.

## Результат

Существующие start_slicing/status/result и native export поддерживают cylindrical_full через штатный CylindricalBackend. Classic и cylindrical сохраняются. Все три режима используют прежние ID/контракты/общий guard/QtBridge/ToolRegistry. Пользователь выбирает режим прежним set_print_mode; новых альтернативных tools/серверов/UI не добавлять.

## Подтверждённая граница

Читайте FIVE_D_SOURCE_NOTES.md и повторно исходники выданного CylindricalBackend, его StartSliceJob, MultiBackend, GenerateBasementJob, ProcessCliJob и backend-регистрацию. Full — составной backend, его нельзя считать CLIParserBackend с другим mode: собственного `_process` parser у него нет, используются подчинённые CuraEngineBackend/CLIParserBackend через native getBackends.

Штатная цепочка: подготовка → основание → CuraEngine → Glicer/ProcessCliJob → CLIParser. `_onSlicingFinishedMessage` после Cura — промежуточный Processing/0.5, финал — `_onCliParserFinishedMessage`. Финальный Done выдаётся до последних замен G-code/сброса флагов. Запускать внешний forceSlice целиком, не переставлять native handlers и не запускать подчинённые движки вручную.

## Реализация

- Сначала кратко сообщить ведущему, какие существующие наблюдения10 можно переиспользовать и где у full иной API. Минимальное расширение существующего наблюдателя; не создавать универсальный pipeline framework ради двух режимов.
- Проверить actual mode/current backend по регистрации, необходимый состав sub-backend, машину/платформу/настройки/модели. Сохранить прежние preflight/auto-slice/preview/busy. Все собственные обращения к API/сигналам/контексту — Qt; native worker остаётся штатным API.
- Привязать стадии/jobs/буфер/процесс к своему внешнему запуску и платформе. Prep/основание/Cura Done, успешный Glicer exit и ProcessCliJob.finished отдельно не завершают run. Учитывать ранние/двойные/быстрые сигналы и публичные job flags в соответствии с исходником конкретной стадии, а не общим предположением.
- Подчинённые процессы Cura/parser могут переиспользоваться, их живой idle не препятствует успеху. Собственный Glicer должен закончиться с кодом0; ошибки jobs/socket/parser/процесса не маскируются. Ожидаемую штатную смену сокета при старте отличать от поздней подмены. Не обходить активацию и не менять дистрибутив.
- Финал только после внешнего parser-final и отложенного Qt-readback: свежий G-code именно текущего slice, завершение всех стадий и последние подтверждённые оценки outer backend → PrintInformation. Учитывать несколько промежуточных оценок; защиту от чужих данных не отключать без доказанного source-пути. Неполные показатели — null/предупреждение по прежнему контракту.
- printing_mode/backend_id в статусе/результате фактические. Принятый результат хранит окончательные chunks; поздняя подмена/изменение G-code и контекста делает его stale. Сохранить привязку G-code/3MF к актуальному slice_id и штатным writers, подтвердить full-mode/settings в проекте. Языковая модель не генерирует траектории.
- Timeout не отменяет живые стадии и не освобождает guard раньше их выхода. Shutdown — прежняя ограниченная readonly-модель10 без kill/wait/новых действий сцены; неизвестный исход и необходимость перезапуска описывать явно. Не добавлять ещё один механизм фонового мониторинга чата.

## Проверка и сдача

Значимые новые проверки: полный и быстрый составной цикл; промежуточный Cura Done не финал; основание и несколько оценок; свой/чужой job/process/платформа; ошибки каждой нужной стадии; parser Done до окончательного буфера; Glicer nonzero; timeout/late/shutdown/guard; stale и native writer harness для full. Сохранить все прежние Python/JS-проверки. Подмены/исследование классов явно отделять от установленного runtime; не расширять тестирование после достаточного успеха без новой причины.
