# Задание: объединение агентной части artem_backend

Назначается ведущим после сохранения и push основы ТЗ 01–07. Прямое разрешение пользователя: «Да сделай как по плану закомичь и пуш все до 07 и потом попробуй слить ну дай это разрабу и так же продолжай следить за ним». Согласованный обзор — docs/reports/INTEGRATION_PLAN_B9C0190.md. Это интеграция существующей работы коллеги, не реализация всего оставшегося хакатона.

## Основа и границы

- Ведущий фиксирует и публикует основу, создаёт ветку `codex/integrate-artem-agent` и начинает настоящий `git merge --no-commit --no-ff origin/artem_backend`. Исполнитель начинает только после сообщения с фактическим состоянием merge.
- Сохранить авторство исходных коммитов ветки. Конфликты разрешать в пользу работоспособной итоговой интеграции. Ведущий проверяет результат, завершает Git-фиксацию и публикацию; исполнитель без отдельного сообщения не делает commit/push/abort/switch/reset/stash.
- Единственная поставка — `plugin/AIAssistant/`. Три старые альтернативные копии `AIAssistant/`, `submission/`, `stereotech_team_submission/` и генераторы не включать в итоговый merge относительно нашей основы. Убирать только добавленные сливаемой веткой файлы после проверки принадлежности путей репозиторию. Исходный код STE и установленную копию не менять.
- Сохранить код, схемы и поведение ТЗ 01–07, общие QtBridge/lock/ModelRegistry/Slicing/Exports. Фиктивный адаптер из ветки не использовать. ТЗ 08, вложения/uploads/downloads, новые операции сцены, custom-профили и 5D-нарезку здесь не реализовывать.
- Python 3.5, api:5, stdlib, без новых зависимостей. Чужие документы, скрипты и Word lock-файлы сохранить.

## Итоговый сценарий

Extension загружается штатным register(app). Пользователь вводит URL/модель/ключ в Qt-диалоге плагина. Открывается браузерный чат: отправка сообщения отвечает 202, результаты приходят polling; агент использует единый текущий реестр, изменения действительно проходят через существующий адаптер. Вопрос «Что умеешь?» не вызывает скрытую настройку/слайсинг. Отсутствие ключа, ошибка сети/LLM или недоступный STE не подменяются успехом.

## Что объединить и исправить

1. **Extension и Preferences.** Сохранить AIAssistant(app), shutdown приложения и остановку сервера/операций. Перенести Qt-диалог настройки, но Preferences читать/писать через существующий bridge.run; из Qt он выполняется прямо, worker ждёт ограниченно. Не создавать второй мост. Сохранение подтверждать; исключения не проглатывать. Не менять кеш успешно до подтверждения Preferences. URL и модель выбирает пользователь, их наличие не означает успешного соединения. Ключ не отдавать ни через status/session/events, ни в логи или исключения. Для браузера достаточно configured/has_key, ввод ключа в Qt. Учесть пустой ввод «не менять» и явное удаление ключа, сохранение между перезапусками требует native-проверки.
2. **Клиент и агент.** Использовать полезный код b9c0190 из agent/llm.py/service.py, стандартный TLS и Chat Completions. Адаптировать к нашим ToolRegistry, UnknownToolError/ValueError, оболочке ok/data/error. Сохранить общий источник схем, без замены реестра и адаптера. get_slicer_state вместо несовместимого get_printer_state. Не объявлять arrange_models или другие отсутствующие инструменты. Диагностический load_model(path) не передавать LLM до доверенного file_id. assistant_status с прежним scaffold-ответом не использовать как источник готовности агентной интеграции. Статусы нового API должны отражать фактические возможности.
3. **Ограничения цикла.** Не более 8 обращений LLM, 16 инструментов, 120 секунд на запрос и 30 секунд на сетевой вызов с учётом остатка. Сеть не на Qt. Один активный turn для всей сцены; идемпотентность по client_message_id и полному принятому содержимому, другой запрос с тем же ID — 409. История ограничена целыми блоками assistant-tool, сохраняются фактические частично выполненные операции при ошибке. Некорректный ответ/аргументы и исключения не оставляют busy навсегда. После неопределённого изменяющего вызова (включая qt_timeout и ошибки начавшейся операции) остановить дальнейшие изменения, явно объяснить, без автоповтора/скрытого fallback. Shutdown не допускает новых инструментов или ответов, меняющих завершённое состояние.
4. **HTTP и MCP.** Новые REST-маршруты добавить с сохранением create_server, /api/health и проверенного dispatch. Не исполнять tools/call без id; сохранить ошибки протокола/валидации. Host/Origin — собственный порт, не любой localhost. Сохранить Content-Type, лимиты JSON/текста, таймаут сокета, static whitelist, CSP/nosniff. Контракт — docs/API_CONTRACT.md: status, sessions, messages, /api/events?session_id=...&after=...; имена полей/ошибки/события соответствуют документу. Возможности attachments/downloads пока false, отсутствие маршрутов явно обозначено. В status не выдавать Preferences. Совместимость прежнего /api/message определить явно: сохранить его документированный legacy-сценарий, не дублирующий случайно выполнение, либо обновить проверку и документировать удаление; не выдавать echo за новый LLM-чат.
5. **SPA и dev.** Использовать UI b9c0190 как временный клиент; изменений дизайна ради оформления не делать. Переделать обращения под общий контракт и истинную диагностику. При обновлении вкладки восстановить оба участника диалога из messages и актуальный курсор без дубликатов. tool_started/tool_finished показывают фактические ошибки и результаты. client_message_id сохраняется для той же попытки при сетевом сбое. Не писать «LLM подключена» только по наличию настройки. Поля с секретом в браузере не нужны. Dev-сервер не создаёт ложную машину/модели и не обещает успешные настройки без STE; не делает настоящих LLM-запросов сам при запуске.
6. **Документация и границы.** Обновить API_CONTRACT, plugin README, PLAN и корневой README точечно, сохранив структуру. Разделить реализованное, проверки с подменами и native. Дать короткую инструкцию frontend-участнику с нужными маршрутами, примерами JSON/событий и отсутствующими пока возможностями. Авторство переносимых фрагментов и b9c0190 указать в отчёте; исходные уведомления сохранять.

## Проверки и отчёт

Сохранить смысл всех 153 прежних проверок. Добавить значимые проверки регистрации Extension с app, Preferences/главного потока и ошибок сохранения; успешного tool-цикла на реальном реестре с подменным app; отсутствия ключа/ошибки LLM без изменений; лимитов; неизвестного/неверного инструмента; остановки после неопределённого изменения; concurrent turn/идемпотентности; истории и HTTP по контракту. Не удалять прежние сценарии ради зелёного набора. Обновлять проверки только при документированном изменении старого демонстрационного поведения. Синтаксис Python 3.5, plugin.json, node --check, git diff --check.

Не вводить реальные ключи и не обращаться к провайдеру; сетевой клиент проверять подменой. Не устанавливать плагин и не запускать физическую печать. Настоящие ответы LLM, UI слайсера, Preview и повторное открытие 3MF остаются для native-приёмки и отмечаются открытыми.

После достаточных проверок завершить ход. Отчёт `docs/reports/AGENT_INTEGRATION_REPORT.md`: источник и перечень объединённых файлов, разрешённые конфликты, не перенесённые старые копии, итоговый контракт для фронта, команды/результат проверок, границы runtime, состояние Git. Не начинать другие этапы до ревью ведущего.
