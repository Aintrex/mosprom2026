# ТЗ 06 Настоящий G code и проект 3MF

Статус: готово к исполнению после ревью ТЗ 05. Ведущий просмотрел реализацию и повторил 121 проверку без отказов; native-приёмка ТЗ 05 ещё открыта. Исполнитель приступает после отдельного сообщения ведущего. Корреляцию slice_id, актуальность результата и общую защиту брать из итогового кода ТЗ 05, не создавать второй источник состояния.

## Цель и границы

Получить result.gcode и project.3mf через штатные writers STE Slicer, относящиеся к одной подтверждённой нарезке classic и её настройкам/сцене. В 3MF должны сохраниться не только mesh, но и проект с машиной, материалами, профилями, overrides и преобразованиями. Наличие ZIP или файла с расширением .gcode само по себе не доказывает успех.

Прочитать AGENTS.md, COORDINATION.md, ТЗ/отчёт 05 и существующий код. Сначала git status. Основные изменения — slicer/, реестр инструментов и lifecycle по необходимости. Не менять SPA/LLM/HTTP-контракт файлов и не переносить генераторы из artem_backend. Python 3.5, stdlib и окружение STE Slicer. Физическую печать не запускать.

## Важные API и поток выполнения

Справочные корни STE-Slicer-master и Uranium-steslicer указаны в AGENTS.md. Обязательно проверить:

- app.getMeshFileHandler().getWriter("GCodeWriter") — штатный GCodeWriter, текстовый режим UTF-8. Он читает engine G-code из scene.gcode_dict для активной платформы, добавляет метаданные/настройки и thumbnail.
- app.getWorkspaceFileHandler().getWriter("3MFWriter") — именно **ThreeMFWorkspaceWriter**, бинарный режим. app.getMeshFileHandler().getWriter("3MFWriter") возвращает mesh writer и сам по себе не сохраняет весь проект. PluginRegistry.getPluginObject при нескольких типах не использовать как неподтверждённый способ выбора workspace writer.
- plugins/3MFWriter/ThreeMFWorkspaceWriter.py дописывает глобальный стек, контейнеры обоих экструдеров и нужные Preferences в ZIP штатного mesh writer. Проверить корректный набор печатных root-узлов активной платформы, группы и child transforms; не передавать камеры/платформу/preview как детали.
- Uranium UM/FileHandler/WriteFileJob.py и plugins/LocalFileOutputDevice/LocalFileOutputDevice.py показывают штатный job: writer/stream/nodes/mode, job.finished, getResult/getError и закрытие stream. Начало job не равно успешной записи; ошибка закрытия/flush тоже провал.
- **Опасность deadlock:** steslicer/Utils/Threading.py: call_on_qt_thread всегда делает callLater и блокирующий Event.wait, даже если вызван из Qt. WorkspaceWriter.write и GCodeWriter._createSnapshot декорированы им. Нельзя вызвать их синхронно внутри нашего bridge.run на Qt — основной поток начнёт ждать самого себя.
- Использовать штатный job/worker для входа в writer, как приложение. Поиск writer, работа с app/сценой/стеками и запуск job из нашего кода — через Qt. Сам job/writer затем работает по своему штатному механизму; не добавлять собственных обращений к app из HTTP-worker. В отчёте явно описать границу потоков штатного writer и наших вызовов. Если обеспечить требования к потоку не получается, вернуть ведущему конкретное противоречие до запуска, не исправлять дистрибутив и не отключать декораторы через inspect/monkeypatch.

Не переписывать сериализацию 3MF или G-code. Не подставлять геометрию по габаритам. Writer подтверждает свой результат, но не актуальность engine-данных: это ответственность нашего preflight по ТЗ 05.

## Инструменты

Минимальный контракт, окончательно согласовать с ведущим по итоговой архитектуре 05:

| Инструмент | Аргументы | Назначение |
| --- | --- | --- |
| export_gcode | {"slice_id":"slice-1"} | Запуск записи настоящего G-code указанной нарезки |
| save_project_3mf | {"slice_id":"slice-1"} | Запуск сохранения проекта этой же сцены/нарезки |
| get_export_status | {"export_id":"export-1"} | Фактический статус записи и готовый артефакт |

Запуск короткий, возвращает export_id/state=queued либо running, не ждёт большую запись в HTTP. Статусы queued/running/completed/failed, progress 0..1 или null. Сохранить {ok,data}/{ok:false,error}, JSON-RPC -32602 и честный dev отказ. Аргументы и ID валидируются, неизвестный ID не заменяется последней операцией.

Для этого этапа оба экспорта требуют актуального completed slice_id и classic: это позволяет получить согласованную пару. Сохранение проекта без нарезки можно добавить отдельным последующим требованием, сейчас оно не нужно. Старые/просроченные/неуспешные slice_id отклоняются **до writer**.

Выходная папка генерируется плагином внутри его области данных, например Resources.getCacheStoragePath()/AIAssistant/exports/<uuid> (публичный getter подтвердить в Uranium Resources.py). Не принимать от LLM произвольный output_path и не писать в исходники/папку дистрибутива. Пользователь не теряет существующие файлы: уникальные имена/папки, без перезаписи. В README указать, как найти и скопировать результаты; диагностический статус может сообщить generated local_directory для прямого MCP, но будущий публичный файловый API работает только по зарегистрированным ID.

Готовый артефакт: artifact_id, file_name, kind=project/gcode, size_bytes, slice_id и источник штатного writer. Одно состояние/реестр только для созданных нами файлов; IDs не являются путями. Скачать произвольный локальный файл через этот механизм нельзя. Новые REST-маршруты и кнопки скачивания в этом ТЗ не реализуются — их подключит общая HTTP/UI-интеграция.

## Завершение корректность и очистка

1. Перед каждым запуском подтвердить slice_id, ту же сцену, stack/backend, платформу и настройки. На всё время native write удержать общую защиту от конкурирующего слайсинга/импорта/изменения параметров; чтения и status доступны. Параллельная запись общими writer-объектами запрещена, особенно 3MF storeArchive.
2. Получить правильный writer, mode и узлы на Qt, открыть временный файл безопасно вне длительной Qt-операции, подписаться на finished до старта и вызвать штатный WriteFileJob. Не открывать Save As и не выбирать диалоги автоматически.
3. completed только после собственного finished, положительного getResult без getError, успешного flush/close, проверки непустого файла и повторного подтверждения соответствия сцене. Использовать временное имя и публиковать итоговый артефакт только после всех проверок. При ошибке не сообщать путь к якобы готовому result.gcode.
4. Структурная проверка project.3mf: читаемый ZIP, штатная 3D/3dmodel.model и сохранённая workspace-конфигурация SteSlicer/, контейнеры/машина/экструдеры. Проверка XML/ZIP не заменяет повторное открытие в STE Slicer. Не переделывать архив самостоятельно ради прохождения проверки.
5. G-code должен быть результатом завершённого engine job своей платформы, не пустой файл с одними заголовками. Сопоставить с исходными данными engine, учитывая штатные заголовки/настройки writer. Физическую пригодность финально проверять штатным Preview на том же принтере/режиме.
6. Если пользователь вручную изменил проект во время записи, не объявлять согласованный артефакт: зафиксировать устаревание/ошибку. Не смешивать старый G-code с новыми настройками, даже если оба файла по отдельности читаются.
7. Конечный бюджет операции — 120 секунд, отдельный запуск/status укладывается в обычный QtBridge. Таймаут после старта не отменяет writer: не закрывать используемый stream и не отпускать защиту до фактического выхода job. Файл не публикуется как успешный; поздний finished безопасно очищает контекст. Если native callback завис из-за ошибки декоратора, сообщить неопределённость и требование перезапуска, не повторять автоматически.
8. Очищать свои подписки/потоки/временные файлы после подтверждённого завершения. Не удалять файл, который ещё пишет job. После ошибки 3MF проверить сброс штатного setStoreArchive(False), если его поддерживает фактический mesh writer, без изменения чужих job/буферов. Shutdown не должен вызывать запись/повторную публикацию или незаметный успешный ответ.

## Проверки

- Нет завершённой нарезки, stale/unknown ID, writer отсутствует, неподдерживаемый mode, engine/экспорт занят — writer не запускается.
- Правильные workspace/mesh handler, text/binary mode, последовательность запуска/finished/закрытия, delayed job и отсутствие блокирующего ожидания Qt.
- Writer false/exception/getError, ошибка открытия/диска/flush/close, пустой/повреждённый файл: нет completed и опубликованного артефакта.
- Изменение сцены/параметров, параллельные запросы, timeout/позднее завершение/shutdown и storeArchive cleanup. Сохранность чужих файлов и невозможность произвольного пути.
- Согласованная пара одной нарезки, правильный реестр артефактов, валидация schemas и старые проверки. Изолированный fake writer не считать native-экспортом.
